# Android開発 学習ノート

このドキュメントは、Androidアプリ開発における重要な概念、OSの挙動、およびライフサイクルに関する学習のまとめです。

## 1. アプリの終了処理（Activityの破棄）
Androidにおけるアプリ画面（Activity）の終了には、タスク履歴の扱いの違いによる2つの主要な方法がある。

- **`finish()`**
  - 現在のActivityを終了する（画面を閉じる）。
  - OS標準の「戻る」操作をした場合もこの処理が呼ばれる。
  - **特徴:** アプリの画面は消えるが、OSの「最近使ったアプリ（タスク履歴）」には残る。履歴から再度開くと、新しくActivityが作り直される。
- **`finishAndRemoveTask()`**
  - 現在のActivityを終了し、さらに「タスク履歴」からも完全に消去する。
  - **特徴:** ユーザーが明示的に「アプリを完全に終了した」という状態を作りたい場合に使用する。

## 2. 画面遷移とバックスタック (Fragment)
Fragmentを使った画面遷移では、OSの履歴管理（バックスタック）をどう扱うかが重要になる。

- **バックスタックに追加する (`addToBackStack`)**
  ```java
  getParentFragmentManager().beginTransaction()
          .replace(R.id.fragment_container, new SecondFragment())
          .addToBackStack(null) // 履歴に残す
          .commit();
  ```
  - 遷移前のFragmentはバックスタックに保存される。
  - スマホの「戻る」操作をすると、OSが自動的に前の画面に戻してくれる。

- **バックスタックに追加しない（ステートマシン的な遷移）**
  - `.addToBackStack(null)` を書かない場合、遷移の履歴はOSに残らない。
  - 次の画面で「戻る」操作をすると、戻る履歴がないためActivity自体が終了する。
  - 独自のステートマシンで状態を管理したい場合は、このアプローチを取り、OSの「戻る」操作は別途ブロックする。

## 3. 「戻る」操作の制御とブロック
OS標準の「戻る」ボタンの挙動は、`OnBackPressedDispatcher` を使って横取り（インターセプト）できる。

```java
OnBackPressedCallback callback = new OnBackPressedCallback(true) {
    @Override
    public void handleOnBackPressed() {
        // 戻る操作時の独自処理（空にすればブロックされる）
    }
};
requireActivity().getOnBackPressedDispatcher().addCallback(getViewLifecycleOwner(), callback);
```
- **利点:** `getViewLifecycleOwner()` と紐付けることで、「そのFragmentが表示されている間だけ」ブロックを有効にできる。

## 4. UIレイアウトとクリック判定 (XML)
画面の見た目はXMLで定義し、Javaコードとは完全に分離される。

- **サイズ指定による当たり判定の違い**
  - `match_parent`: 親要素（画面全体）に広がる。どこをタップしても反応するようになる。
  - `wrap_content`: 中身（文字など）のサイズに縮まる。文字の部分だけがタップ可能になる。
- **ViewGroup (レイアウト)**
  - `LinearLayout`: 要素を縦(`vertical`)や横(`horizontal`)に順番に並べる。
  - `ConstraintLayout`: バネのように制約をかけて配置する（現在のAndroid開発の主流）。

## 5. メモリ管理とライフサイクル (ガベージコレクション)
組み込み開発（手動メモリ管理）とは異なり、AndroidではOS（ART環境）とガベージコレクション（GC）がメモリを管理する。

- **バックスタック内のメモリ状態**
  - 画面Aから画面Bへ遷移し、画面Aをバックスタックに残した場合：
    - **解放される:** 画面Aの見た目（View群）。重いUIリソースは破棄される。
    - **保持される:** 画面AのFragmentインスタンス。入力データなどの状態は残る。
- **メモリリークと断片化**
  - **断片化:** GCにはコンパクション（メモリの再配置・圧縮）機能があるため、オブジェクトの生成・破棄を繰り返しても、C言語のような深刻なメモリ断片化による確保失敗は起きにくい。
  - **メモリリーク:** 基本的に自動回収されるが、「破棄された画面の参照を、裏の通信処理などが保持し続けてしまう」というユーザー由来の解放漏れは発生し得る。
  - これを防ぐため、OSの仕組み（ライフサイクル）に沿って適切にコールバックを登録/解除することが重要となる。

---
**開発の心得:**
「OSがよしなにやってくれる」機能が多い反面、OSの都合（画面回転による再生成、メモリ逼迫による裏側での破棄）で予期せぬ動きをすることがある。
『自分が作ったプログラムの動き』と『OS標準の動き』の境界線を意識し、必要に応じてOSの挙動をコントロール（インターセプト）していくことが重要。
