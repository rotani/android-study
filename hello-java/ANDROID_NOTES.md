# Android開発 学習ノート

このドキュメントは、Androidアプリ開発における重要な概念、OSの挙動、およびライフサイクルに関する学習のまとめです。

## 1. アプリの終了処理（Activityの破棄）
Androidにおけるアプリ画面（Activity）の終了には、タスク履歴の扱いの違いによる2つの主要な方法がある。

- **`finish()`**
  - 現在のActivityを終了する（画面を閉じる）。
  - OS標準の「戻る」操作をした場合もこの処理が呼ばれる。
  - **特徴:** アプリの画面は消えるが、OSの「最近使ったアプリ（タスク履歴）」には残る。履歴から再度開くと、新しくActivityが作り直される。
- **`finishAndRemoveTask()`**
  - 現在のActivityを終了し、さらに「タスク履歴」からも完全に消去する。
  - **特徴:** ユーザーが明示的に「アプリを完全に終了した」という状態を作りたい場合に使用する。

- **Android 12以降の「戻る」ボタンの挙動変更**
  - Android 12以降では、ルート（最初）のActivityで「戻る」ボタンを押しても `finish()` されず、ホームボタンを押した時のように**「バックグラウンドに隠す」だけ**の挙動がデフォルトになった。
  - アプリを完全に終了させたい場合は、従来通り `OnBackPressedDispatcher` で戻る操作を横取りし、明示的に `finishAndRemoveTask()` を呼ぶ必要がある。

## 2. 画面遷移とバックスタック (Fragment)
Fragmentを使った画面遷移では、OSの履歴管理（バックスタック）をどう扱うかが重要になる。

- **バックスタックに追加する (`addToBackStack`)**
  ```java
  getParentFragmentManager().beginTransaction()
          .replace(R.id.fragment_container, new SecondFragment())
          .addToBackStack(null) // 履歴に残す
          .commit();
  ```
  - 遷移前のFragmentはバックスタックに保存される。
  - スマホの「戻る」操作をすると、OSが自動的に前の画面に戻してくれる。

- **バックスタックに追加しない（ステートマシン的な遷移）**
  - `.addToBackStack(null)` を書かない場合、遷移の履歴はOSに残らない。
  - 次の画面で「戻る」操作をすると、戻る履歴がないためActivity自体が終了する。
  - 独自のステートマシンで状態を管理したい場合は、このアプローチを取り、OSの「戻る」操作は別途ブロックする。

## 3. 「戻る」操作の制御とブロック
OS標準の「戻る」ボタンの挙動は、`OnBackPressedDispatcher` を使って横取り（インターセプト）できる。

```java
OnBackPressedCallback callback = new OnBackPressedCallback(true) {
    @Override
    public void handleOnBackPressed() {
        // 戻る操作時の独自処理（空にすればブロックされる）
    }
};
requireActivity().getOnBackPressedDispatcher().addCallback(getViewLifecycleOwner(), callback);
```
- **利点:** `getViewLifecycleOwner()` と紐付けることで、「そのFragmentが表示されている間だけ」ブロックを有効にできる。

## 4. UIレイアウトとクリック判定 (XML)
画面の見た目はXMLで定義し、Javaコードとは完全に分離される。

- **サイズ指定による当たり判定の違い**
  - `match_parent`: 親要素（画面全体）に広がる。どこをタップしても反応するようになる。
  - `wrap_content`: 中身（文字など）のサイズに縮まる。文字の部分だけがタップ可能になる。
- **ViewGroup (レイアウト)**
  - `LinearLayout`: 要素を縦(`vertical`)や横(`horizontal`)に順番に並べる。
  - `ConstraintLayout`: バネのように制約をかけて配置する（現在のAndroid開発の主流）。

## 5. メモリ管理とライフサイクル (ガベージコレクション)
組み込み開発（手動メモリ管理）とは異なり、AndroidではOS（ART環境）とガベージコレクション（GC）がメモリを管理する。

- **バックスタック内のメモリ状態**
  - 画面Aから画面Bへ遷移し、画面Aをバックスタックに残した場合：
    - **解放される:** 画面Aの見た目（View群）。重いUIリソースは破棄される。
    - **保持される:** 画面AのFragmentインスタンス。入力データなどの状態は残る。
- **メモリリークと断片化**
  - **断片化:** GCにはコンパクション（メモリの再配置・圧縮）機能があるため、オブジェクトの生成・破棄を繰り返しても、C言語のような深刻なメモリ断片化による確保失敗は起きにくい。
  - **メモリリーク:** 基本的に自動回収されるが、「破棄された画面の参照を、裏の通信処理などが保持し続けてしまう」というユーザー由来の解放漏れは発生し得る。
  - これを防ぐため、OSの仕組み（ライフサイクル）に沿って適切にコールバックを登録/解除することが重要となる。

## 6. MVVMアーキテクチャとステートマシン
Androidのモダンなアプリ開発では、役割を明確に分離するMVVM（Model-View-ViewModel）アーキテクチャが推奨される。

- **役割分担における注意点（MVCからの脱却）**
  - **View (XML / Activity / Fragment):** 画面の描画とユーザー操作の受け付けのみを担当。**FragmentはControllerではなくViewの一部**であり、自身では「次の画面が何か」を知らない「バカなコンポーネント」に徹する。
  - **ViewModel:** アプリの「状態（State）」を保持・管理する責任者であり、ViewとModelの**仲介役（現場監督）**。AndroidのUI部品（View）への依存（知識）を一切持ってはならない。また、データの実体は保持せず、Modelから取得したデータをViewへ横流しする。
  - **Model:** データの保持とビジネスロジック（絶対的なルール）を担当する。画面（UI）のことは一切知らない。
- **単方向データフロー (Unidirectional Data Flow)**
  1. `Fragment` がタップなどのイベントを `ViewModel` に**報告**する。
  2. `ViewModel` が内部の状態（例: `AppState.PAGE_2`）を**更新**する。
  3. 状態変化を監視（Observe）している `Activity` が、新しい状態に合わせて画面を**切り替える**。
  - この一方通行の流れにより、密結合を防ぎ、バグの特定が容易な「疎結合」な設計が実現できる。

## 7. LiveDataとライフサイクルの落とし穴
ViewModelの「状態」をViewへ伝えるために `LiveData`（と `Observer`）を使用するが、Android特有の挙動に注意が必要である。

- **無駄な再生成を防ぐガード処理**
  - `LiveData` は、Viewが監視を始めた瞬間に「最新の値を1度通知してくる」という強い性質を持つ。
  - 画面回転などでActivityが再生成された際、**「OSによるFragmentの自動復元」**と**「LiveDataからの初期通知による画面上書き」**が競合し、入力中のテキストなどが消えてしまうバグの温床になる。
  - これを防ぐため、Activityの監視処理（`onChanged`）内では、`currentFragment instanceof TargetFragment` のように「現在表示されている画面」をチェックし、**本当に必要な時だけ新しくFragmentを生成（`new`）して入れ替えるガード処理**が不可欠となる。

## 8. フォルダ構成（パッケージ管理）のアプローチ
ファイルが増えてきた際のパッケージ分けには、大きく2つの流派がある。

- **レイヤー別 (Package by Layer):**
  - `ui/`, `viewmodel/`, `model/` のようにアーキテクチャの役割ごとにフォルダを分ける。構造が可視化されやすい。
  - パッケージを分けた瞬間から、別パッケージのクラスを使うために Java の明示的な `import` が必要になる。
- **機能・画面別 (Package by Feature):**
  - `main/`（メイン画面に関するUIとViewModelを一式入れる）のように機能ごとに分ける。近年の大規模アプリ開発での主流。
- **実践的なアプローチ（エントリポイントの特別扱い）**
  - アプリの入り口である `MainActivity` はあえてルートパッケージに残し、Fragment等を `ui/` 配下に移動するスタイルも現場でよく採用される。これにより `AndroidManifest.xml` の変更リスクを避けつつ構造を整理できる。
  - この場合、ルートに自動生成されるリソース管理の `R` クラスを使用するために、サブパッケージ側で `import com.example.hello.R;` のような明示的なインポートが必須となる。

## 9. Model層の分離と POJO (Plain Old Java Object)
Model層（例：`UserModel`）は、Androidのフレームワーク（`Activity` や `Fragment` など）を一切継承しない**純粋なJavaクラス（POJO）**として作成することが推奨される。

- **POJOでModelを作るメリット**
  - **爆速のユニットテスト:** Android OSの重いシミュレータを起動することなく、「文字数チェックが正しいか」といったコアなロジックをパソコン上で瞬時にテストできる。
  - **ライフサイクルからの隔離:** OSが勝手に再生成や破棄を行うView層から切り離されるため、純粋に「データとルール」に集中できる。
  - **再利用性:** Androidに依存していないため、将来的に同じJava系言語でサーバー側のプログラムを作る際などに使い回すことが可能。
- **データとロジックのカプセル化**
  - 「ユーザーの名前（データ）」と「空文字はNG（ルール）」は常にセット（同じクラス内）にまとめる。ViewModelにデータを持たせてしまうと、このカプセル化が崩れてしまう。

## 10. Viewの状態自動保存・復元 (SavedInstanceState)
Android OSには、ユーザーの入力中のデータを守るための「おせっかい機能」が備わっている。

- **自動復元の条件と挙動**
  - `android:id` が設定されている入力フォーム（`EditText` など）は、画面回転による破棄・再生成時や、バックグラウンドからタスク履歴経由で復帰した際に、**OSが自動で中身（入力中の文字）を記憶し、復元する**。
  - これにより、意図せず「前の画面に戻ったのに文字が残っている」という現象が起きることがある。状態を完全にリセットしたい場合は、画面破棄時に明示的にデータをクリアするか、Activity自体を完全に終了（`finishAndRemoveTask`）させる必要がある。

## 11. オブジェクト指向の落とし穴と歴史的背景
Android開発の歴史の中で生まれた設計の課題と、現在のモダンなアプローチについて。

- **「継承よりコンポジション」と BaseFragment の罠**
  - かつては共通処理をまとめた親クラス（`BaseActivity` や `BaseFragment`）を作る設計が流行したが、様々な機能が詰め込まれて全貌が分からない「Fat Base Class（神クラス）」を生み出すアンチパターンとなった。
  - 現在は深い継承ツリーを避け、必要な機能を持った独立した小さなクラス（部品）を作り、画面クラスがそれを保持して呼び出す「コンポジション（包含・委譲）」が推奨されている。これはC言語における「構造体の中に別の構造体のポインタを持つ」設計思想と同じである。
- **Javaの省略文化とIDEへの依存**
  - Javaには「ローカル変数と被らなければ `this.` を省略してよい」という文化や、メンバ変数の頭に `m` を付ける（例: `mLogger`）という古い規約が存在した。
  - 現在のJava開発は、Android StudioなどのIDEによる色分け（シンタックスハイライト）に依存して変数のスコープを見分けるのが前提となっており、プレーンなテキストとして読むと「この変数は誰が持っているのか？」が非常に追いづらい。
  - こうしたJavaの冗長さ（ボイラープレート）やNullの危険性を、言語仕様レベルで安全かつシンプルに解決するために生まれたのが **Kotlin** である。

## 12. View Bindingによる安全なUI操作とメモリ管理
従来の `findViewById` を用いたUI部品の取得は、実行時クラッシュ（NullPointerExceptionやClassCastException）の温床であり、View層のコードを肥大化させる原因となっていた。

- **View Bindingの仕組みと利点**
  - `build.gradle` で有効化すると、XMLファイルごとに専用のBindingクラス（例: `FragmentMainBinding`）がビルド時に自動生成される。
  - これを包含（コンポジション）して使うことで、コンパイル時に型安全・Null安全が保証され、安全かつ簡潔なUI操作が可能になる。
- **Fragmentにおけるメモリリーク対策（鉄則）**
  - Fragmentのインスタンス（Javaオブジェクト）は、画面の描画（View）が破棄された後も生き残る場合がある。
  - この時、Bindingクラスの参照を持ったままだと、ガベージコレクション（GC）がViewのメモリを回収できずメモリリークを引き起こす。
  - これを防ぐため、Fragmentでは必ず `onDestroyView()` のタイミングで `binding = null;` とし、明示的に参照を切る必要がある。

---
**開発の心得:**
「OSがよしなにやってくれる」機能が多い反面、OSの都合（画面回転による再生成、メモリ逼迫による裏側での破棄）で予期せぬ動きをすることがある。
『自分が作ったプログラムの動き』と『OS標準の動き』の境界線を意識し、必要に応じてOSの挙動をコントロール（インターセプト）していくことが重要。
また、設計においては「誰が何を知っているべきか（責務の分離）」を常に問い続けることで、堅牢なアーキテクチャを維持できる。

## 13. Single Activity Architecture と SPA
モダンなAndroid開発では、WebフロントエンドのSPA（Single Page Application）と同様の思想である「Single Activity Architecture」が主流となっている。

- **SPAとしてのFragment運用**
  - アプリ全体で `Activity` は1つ（巨大な空箱）にし、画面の切り替えは `Fragment` の入れ替えで行う。
  - 音声アシスタントのように「画面レイアウトは同じまま、状態（色や文字）だけが変わる」場合は、1つのFragmentの中でViewModelを用いたステートマシンを回すのが最適（究極のSPA）。
- **ルーティング（画面の差し替え）**
  - 設定画面や履歴画面など「全く別のレイアウト」が必要になった場合は、新しいActivityを作るのではなく、新しいFragmentを作り、MainActivityの空箱の中で入れ替える。
  - これにより、「1画面内での状態変化（ステートマシン）」と「別機能への切り替え（ルーティング）」という二正面からの柔軟な拡張が可能になる。

## 14. Thin Clientとしてのマルチモーダル拡張の可能性
Androidを「Thin Client（薄いクライアント）」とし、重い処理をクラウドに任せるアーキテクチャは、極めて高い拡張性を持つ。

- **スマホの機能（センサー・Intent）との連携**
  - カメラで撮った「画像」や、他アプリからIntent（共有機能）で送られた「テキスト」などを、ViewModelの新たな状態（コンテキスト）として簡単に保持できる。
  - これらを音声データと共にCloud RunのGateway LLM（Gemini等）へ送ることで、スマホ特有の機能をフル活用したマルチモーダルなアシスタントが実現可能。
  - ステートマシン（`LISTENING` や `THINKING`）のUI遷移ロジックを一切壊すことなく、送受信するデータの中身だけを拡張していけるのがMVVMの大きな強みである。

## 15. 非同期処理とハードウェアリソースの管理
マイク（`AudioRecord`）などのハードウェア制御は、UIスレッドをブロックしないよう裏スレッドで実行する必要がある。

- **バッファの使い回しによるGC回避**
  - 録音ループ内で毎回バッファ配列を `new` すると、ガベージコレクション（GC）が頻発して音飛び（プチフリーズ）の原因になる。同じ配列を上書きし続けるのがパフォーマンスチューニングの鉄則。
- **スレッドの自然死とリソース解放**
  - スレッドは無限ループのフラグ（`AtomicBoolean` など）を折って安全に抜け出させ、自然終了（DEAD状態）させる。
  - ハードウェアリソースは有限であり、使い終わったら必ず `release()` を呼んでOSに返却しないと、他アプリ（通話アプリ等）が機能しなくなる致命的なバグを引き起こす。

## 16. バックグラウンド制限と Service 層の必要性
Android 9以降、プライバシー保護の観点から強力な制限が追加された。

- **バックグラウンドでのマイク無音化**
  - アプリが裏に回った（画面から見えなくなった）瞬間、OSはマイクの入力を物理的に遮断し、アプリには「無音（0）」のデータしか渡らなくなる。
  - 裏で録音や通信を継続したい場合は、通知を出し続ける **Foreground Service（フォアグラウンドサービス）** として明示的にOSへ宣言する必要がある。これがアーキテクチャにおける `Service` 層の真の役割の一つである。

## 17. ストリーミングにおけるプロデューサー・コンシューマー問題
マイクから拾った生音声（PCM）をリアルタイムにネットワークへ送信する場合、バックプレッシャー（背圧）の考慮が必須となる。

- **バッファ詰まりの回避**
  - 録音スレッド内で直接通信処理を行うと、ネットワーク遅延時に録音処理ごとブロックされ、音の欠落に繋がる。
  - これを防ぐため、「録音（プロデューサー）」と「通信（コンシューマー）」のスレッドを分離し、間にキューを挟む設計が求められる。キューが溢れた場合のハンドリング（破棄やエラー終了）をどうするかが設計の肝となる。

## 18. UIの非同期イベントと「連打防止（デバウンス）」の鉄則
ボタンの連続タップによる「レースコンディション（競合状態）」は、Android開発で最も頻発するバグの一つである。

- **権限要求ダイアログの罠**
  - `checkSelfPermission` から `requestPermissionLauncher.launch()` を呼んでダイアログが出るまでには非同期のラグがある。この隙にボタンを連打されると、OSへのリクエストが重複し、OSがパニックを起こして不正な状態遷移（権限がないのに処理が進む等）を引き起こすことがある。
- **二重タップ防止（デバウンス処理）と状態ロック**
  - **デバウンス:** `System.currentTimeMillis()` を用いて、前回クリック時から一定時間（例: 500ms）以内のイベントを無視する。
  - **状態ロック:** 非同期処理（権限要求やネットワーク通信）を開始する直前にフラグ（`isRequesting`）を立て、コールバックで戻るまでUI操作を無視する。
  - この2つの防壁をView層に設けることで、ユーザーの予期せぬイレギュラー操作からアプリのステートマシンを守ることができる。

## 19. パーミッション要求のUXと永久拒否への対応
Androidの権限要求において、ユーザー体験（UX）を損なわないための設計は公開アプリにおけるベストプラクティス（必須要件）である。

- **「永久拒否」の仕様と落とし穴**
  - ユーザーが権限リクエストを複数回拒否すると、OSは「この権限は絶対に与えない」と判断し、以降はアプリが要求してもダイアログを一切表示しなくなる。
  - この状態に陥ると、ユーザーは「ボタンを押しても何も起きない（アプリが壊れた）」と勘違いしてアンインストールする原因となる。
- **設定画面への親切な誘導 (Intentの活用)**
  - `shouldShowRequestPermissionRationale()` を用いて永久拒否状態を判定する。
  - 永久拒否されている場合は放置せず、「設定から許可してください」という自作ダイアログを出し、`Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS)` を使ってOSの深い設定画面（アプリ情報）へワンタップでワープさせる救済措置を実装するのが鉄則である。

## 20. 実機デバッグとLogcatの確認方法 (WebADB)
Android Studio等の重いローカル開発環境がなくても、WebUSB技術を利用してブラウザから直接スマホ実機のログ（Logcat）を確認できる。

- **WebADBを使ったログ確認手順**
  1. **スマホの準備:** スマホの設定から「ビルド番号」を連打して開発者モードを有効にし、**「USBデバッグ」**をONにする。
  2. **PCと接続:** スマホをPCにUSBケーブルで接続する。
  3. **WebADBにアクセス:** Chrome または Edge ブラウザで [WebADB](https://app.webadb.com/) を開く。
  4. **デバイス接続:** 左上の「Add Device」からスマホを選択して接続（スマホ画面に許可ダイアログが出たら承認する）。
  5. **Logcatの確認:** メニューの「Logcat」を開き、検索窓で特定のタグ（例: `AudioRecorderHelper`）をフィルタリングすることで、アプリの裏側（スレッドの動きやデータの取得状況）をリアルタイムに監視できる。
  - **利点:** クラウド開発環境（Codespaces等）からビルドしたAPKを実機にインストールして動作確認する際、この手法を使えばPCに何もインストールせずにプロ並みのデバッグが可能となる。

## 21. Repositoryパターンによるデータ層の分離
ViewModelと、データの取得・保存先（マイク、ネットワーク、DB等）の間に「総合窓口」を設ける設計パターン。

- **目的と役割**
  - ViewModelから、データソース（マイク、API等）に関する複雑な実装を完全に隠蔽（カプセル化）する。
  - ViewModelはRepositoryに「データ取ってきて」と依頼するだけでよく、その裏でどうやってデータを取得しているか（スレッド管理、キューイング、AIDL等）を知る必要がなくなる。
- **メリット**
  - **関心の分離:** ViewModelはUIの状態管理に、Repositoryはデータの管理にそれぞれ専念できる。
  - **拡張性と疎結合:** データソースを変更する修正がRepository内部で完結し、UIに影響しない。

- **【発展】単一責任の原則（SRP）と広義のRepository**
  - 厳密なオブジェクト指向の観点では、「ハードウェア操作の隠蔽（Facade）」と「データの一時保管（Buffer/Queue）」は別々の責務であるため、1つのRepositoryが両方を持つのは単一責任の原則に反する可能性がある。
  - しかし、Android開発の実務においては、ViewModelから見た「外部世界の総合窓口」として、これらを一旦広義の「Repository」としてまとめるアプローチがよく取られる（過度な抽象化の回避）。
  - 将来的に通信機能などが追加されRepositoryが肥大化（神クラス化）した場合は、さらに上の層として「Use Case（ユースケース）層」を導入し、Repositoryは純粋なデータアクセスのみに特化させる、といったリファクタリングが次の設計ステップとなる。

## 22. アーキテクチャの可視化（クラス図とシーケンス図）
複雑なシステムを構築する際、Mermaid等を用いて設計を可視化することはアーキテクトの重要な責務である。

- **クラス図（静的構造）:** 誰が誰を知っているか（依存の方向）を可視化する。UIからデータ層への「一方通行」と、インターフェースを利用した「依存関係逆転の原則（DIP）」を確認できる。
- **シーケンス図（動的振る舞い）:** 処理の時間軸とスレッドの境界を可視化する。重い処理が裏スレッドに委譲されているか、キューによるバックプレッシャー（背圧）の防波堤が機能しているかを証明できる。
